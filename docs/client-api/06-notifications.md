# Notifications

Notification endpoints let clients retrieve and manage the authenticated user's notifications. Notifications are generated by social interactions (mentions, follows, favourites) and by Corundum-specific protocol events. Clients that want notifications as they happen subscribe to the `notifications` topic of the event stream (`14-event-stream.md`); these HTTP endpoints are for the initial load and for catching up.

## Endpoints

### GET /api/corundum/v1/notifications

Returns the authenticated user's notifications, newest first.

**Authentication:** Required (`read:notifications` scope).

**Query Parameters:**

| Parameter | Type | Default | Description |
|-----------|------|---------|-------------|
| `cursor` | string | — | Opaque pagination cursor from a previous response (`00-design.md`, Pagination) |
| `before` | string (RFC 3339) | — | Only notifications created strictly before this time |
| `after` | string (RFC 3339) | — | Only notifications created strictly after this time |
| `limit` | integer | 15 | Maximum number of results (max 30) |
| `exclude_types[]` | array of strings | — | Exclude notifications of these types (see type list below) |
| `types[]` | array of strings | — | Include only notifications of these types. Mutually exclusive with `exclude_types[]`. |
| `account_id` | string (DID) | — | Return only notifications from this account |

`types[]` and `exclude_types[]` are mutually exclusive. If both are provided, the operator returns a 422 error.

**Returns:** PaginatedResponse of Notification entities, newest first.

**Errors:**

| HTTP status | Code | Meaning |
|-------------|------|---------|
| 400 | `INVALID_CURSOR` | The cursor fails verification or was issued for a different request |
| 401 | `UNAUTHORIZED` | No valid token provided |
| 403 | `INSUFFICIENT_SCOPE` | Token lacks `read:notifications` scope |
| 422 | `VALIDATION_FAILED` | Both `types[]` and `exclude_types[]` were specified |

---

### GET /api/corundum/v1/notifications/:id

Returns a single notification by ID.

**Authentication:** Required (`read:notifications` scope).

**Path Parameters:**

| Parameter | Description |
|-----------|-------------|
| `:id` | The notification ID (operator-local, opaque) |

**Returns:** Notification entity.

**Errors:**

| HTTP status | Code | Meaning |
|-------------|------|---------|
| 401 | `UNAUTHORIZED` | No valid token provided |
| 403 | `INSUFFICIENT_SCOPE` | Token lacks `read:notifications` scope |
| 404 | `NOT_FOUND` | No notification with that ID, or it belongs to a different user |

---

### POST /api/corundum/v1/notifications/clear

Deletes all notifications for the authenticated user. This action is irreversible.

**Authentication:** Required (`write:notifications` scope).

**Request Body:** None.

**Returns:** Empty object `{}`.

**Errors:**

| HTTP status | Code | Meaning |
|-------------|------|---------|
| 401 | `UNAUTHORIZED` | No valid token provided |
| 403 | `INSUFFICIENT_SCOPE` | Token lacks `write:notifications` scope |

---

### POST /api/corundum/v1/notifications/:id/dismiss

Dismisses (deletes) a single notification by ID.

**Authentication:** Required (`write:notifications` scope).

**Path Parameters:**

| Parameter | Description |
|-----------|-------------|
| `:id` | The notification ID to dismiss |

**Request Body:** None.

**Returns:** Empty object `{}`.

**Errors:**

| HTTP status | Code | Meaning |
|-------------|------|---------|
| 401 | `UNAUTHORIZED` | No valid token provided |
| 403 | `INSUFFICIENT_SCOPE` | Token lacks `write:notifications` scope |
| 404 | `NOT_FOUND` | No notification with that ID, or it belongs to a different user |

## Notification Types

Corundum supports the standard Mastodon notification types plus three types for Corundum-specific protocol events.

| Type | Trigger |
|------|---------|
| `mention` | Someone mentioned you in a status |
| `reblog` | Someone reblogged (boosted) one of your statuses |
| `favourite` | Someone favourited one of your statuses |
| `follow` | Someone followed you |
| `follow_request` | Someone sent a follow request (only for locked accounts) |
| `poll` | A poll you voted in, or a poll you created, has ended |
| `status` | Someone you enabled notifications for posted a new status |
| `corundum.reply_rejected` | A reply you submitted was rejected by the operator of the post you replied to |
| `corundum.account_migrated` | An account you follow now names a new operator in its DID document |
| `corundum.curation_flagged` | A subscribed curator has applied a label to one of your statuses |

### corundum.reply_rejected

A reply is accepted or rejected by the operator of the post being replied to (spec Chapter 21). When that operator rejects a reply submission, it returns a `REPLY_REJECTED` error whose `details.reason` says why: `blocked-user`, `replies-disabled`, `curation-match`, `policy-violation`, and the other reason codes of spec Chapter 21. Your operator turns the rejection into a `corundum.reply_rejected` notification instead of discarding it silently.

The reply still exists in your own timeline; it is simply not part of the other post's reply tree. You know which post rejected it and why. In particular, a `blocked-user` rejection tells you that the author of that post has blocked you. Corundum does not pretend a block can be hidden from the person blocked (`07-relationships.md`).

### corundum.account_migrated

Raised when your operator re-resolves the DID of an account you follow and finds that its DID document names a new operator endpoint. The operator re-resolves after receiving a MigrationNotification (which is only a hint) or when its cached copy of the DID document expires, which is never more than 24 hours (spec Chapter 7). The account's `id` does not change, because the DID does not change; your follow keeps working without any action on your part. The notification exists so that a client can show that the account moved.

### corundum.curation_flagged

Delivered when a curator that you or your operator subscribes to applies a label to one of your own statuses. The notification carries the full CurationLabel, including the curator's `authority` and `appeal_url`, so you can file an appeal (`11-curation.md`).

## Notification Entity

Notification entities include the following fields:

| Field | Type | Description |
|-------|------|-------------|
| `id` | string | Notification ID (operator-local, opaque) |
| `type` | string | Notification type (see table above) |
| `created_at` | string (ISO 8601) | When the notification was created |
| `account` | Account entity | The account that triggered the notification |
| `status` | Status entity or null | The relevant status, if applicable to this notification type |
| `corundum` | object or null | Corundum-specific fields; present only for `corundum.*` notification types |

For `corundum.reply_rejected`, `status` is your rejected reply, `account` is the author of the post you replied to, and the `corundum` object contains:

```json
{
  "corundum": {
    "rejected_status_id": "<activity id>",
    "reason": "blocked-user"
  }
}
```

For `corundum.account_migrated`, `account` is the account that moved, and the `corundum` object contains:

```json
{
  "corundum": {
    "previous_operator": "https://a.example",
    "operator_endpoint": "https://b.example"
  }
}
```

For `corundum.curation_flagged`, `status` is your labeled status, and the `corundum` object contains the CurationLabel entity (`02-entities.md`):

```json
{
  "corundum": {
    "label": { "...": "CurationLabel entity" }
  }
}
```
